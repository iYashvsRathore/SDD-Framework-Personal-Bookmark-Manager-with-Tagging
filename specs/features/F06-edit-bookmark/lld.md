## 1. Design Overview

F06 adds `PUT /api/bookmarks/:id`, reusing F01's `validateUrl`/`normalizeUrl` and F02's `tagService.normalizeAndValidate` verbatim (HLD §6.3, P6) rather than re-implementing either. Three things are genuinely new: the duplicate lookup excludes the record's own id (INV-04), `created_at` is never rewritten (INV-10), and two failure modes that creation never faces — the row having been soft-deleted elsewhere (`NOT_FOUND`) and the row having been edited elsewhere since the dialog opened (`EDIT_CONFLICT`, new in HLD v3 via **AMD-003**, applied this session).

On the `web` side, F06 does **not** add a second dialog. Per C-F06-02/C-F06-03 and `docs/mockup.html`'s `openForm(b)`, the existing `BookmarkForm`/`BookmarksStore` (F01, extended by F02's tags and F03's list) grow an `editing` slice: the same `<dialog>`, the same tag-chip input, the same focus trap and `Esc` handling, switched by whether `store.editing()` is set. Two existing-but-unwired pieces of UI are wired here: F03's rendered-but-handlerless _Edit_ button, and F01's `editExisting` output from the duplicate banner (unused since F01 shipped, because nothing consumed it until now).

## 2. Alternatives Considered

All four decisions were presented to dev-1 with option tables on 2026-10-01 and answered "Accepted A". A fifth question — whether to raise and apply the architecture amendment `EDIT_CONFLICT` requires — was answered "Option A: raise AMD-003, apply it before finalizing the LLD" and is recorded in §12, not here, because it selects an amendment path rather than a feature-local design.

### LD-01 Edit-conflict transport (the mechanism behind C-F06-01's optimistic concurrency)

| Option                                                                                                                                                                                                                     | Pros                                                                                                                                                                                                                                                                     | Cons                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A: a JSON body field `updatedAt`, compared by exact string equality against the stored row's `updated_at`; missing, wrong-typed, or mismatched all fail the SAME way — `409 EDIT_CONFLICT`, never coerced or defaulted** | Consistent with the rest of this API (no other route uses a conditional header); trivial to test with two sequential service calls; failing closed means a client that forgets to send it can never silently overwrite (S1 — the server decides, not the client's claim) | A client must remember to carry the field forward from whatever it loaded                                                                                                                                                                 |
| B: `If-Match`/`ETag` conditional-request headers                                                                                                                                                                           | The standard HTTP mechanism for this exact problem                                                                                                                                                                                                                       | No other endpoint in this API uses custom headers; adds ETag generation/parsing for one route; `ApiService` would need a second calling convention for one method — the same cost class F03's LD-04 already rejected for a lesser benefit |

**Decision:** A (dev-1, 2026-10-01, "Accepted A").
**Trade-off accepted:** the conflict token travels as an ordinary body field rather than a header, in exchange for not introducing a second request-shaping convention into this API for one route.
**Challenge applied:** _what breaks at 1,000 records?_ Nothing — the comparison is a single string equality against a row already fetched by id, no scan. _On restart?_ `updated_at` is persisted exactly like every other column, so a conflict check behaves identically immediately after a restart. _Keyboard-only?_ Unaffected — this is a data-shape decision with no UI surface of its own; §6 covers how the resulting error is presented.

### LD-03 Where the edit dialog's pre-fill data comes from

| Option                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Pros                                                                                                                                                                                                                                                                     | Cons                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A: the row's _Edit_ button reuses the `BookmarkListItem` already held by `BookmarksStore.items()` (it already carries `url`, `title`, `tags`, `updated_at` — F03's `Bookmark`/`BookmarkListItem` interfaces). The "Edit existing" trigger from the duplicate banner (F06-AC12) is served by enriching the ALREADY-shared `duplicateUrlError()` builder's `details` object with `tags` and `updatedAt` (one extra `listTagsForBookmarks` call in the service, for the row already fetched)** | No new route. Matches the mockup's zero-round-trip `openForm(b)` exactly. `duplicateUrlError()` is the one place F01 and F06 already share (`app-error.js`, P6) — enriching it benefits both callers from a single edit, rather than adding two separate response shapes | Touches F01's already-reviewed `duplicateUrlError()` — additive only: the existing `{ title, url }` keys are untouched, `tags`/`updatedAt` are new optional keys. The row-button path's `updated_at` is only as fresh as the page's last `loadList()`; this is benign because staleness here can only ever cause a safe false-positive `EDIT_CONFLICT` (never a silent overwrite — LD-01 fails closed) |
| B: add `GET /api/bookmarks/:id`; both triggers fetch fresh data before opening the dialog                                                                                                                                                                                                                                                                                                                                                                                                     | Freshest possible `updated_at` for both triggers; one single mechanism                                                                                                                                                                                                   | A new route plus an extra round trip on every _Edit_ click for data the UI usually already holds; breaks from this app's existing idiom of refreshing through `loadList()` rather than per-item `GET`s (no other feature does this)                                                                                                                                                                    |

**Decision:** A (dev-1, 2026-10-01, "Accepted A").
**Trade-off accepted:** the row-button path's pre-fill can be up to one `loadList()` cycle stale, in exchange for zero new routes and zero new round trips. A stale `updated_at` can only ever produce a safe, correctable `EDIT_CONFLICT` — never an overwrite — because LD-01 fails closed on any mismatch.
**Challenge applied:** _what breaks on a title-fetch failure?_ Unrelated — pre-fill never touches the fetcher. _On restart?_ `updated_at` is reloaded fresh on the next `loadList()` after a restart, same as every other field. _Keyboard-only?_ Unaffected — this is a data-sourcing decision, not an interaction one.

### LD-04 How the dialog itself represents "add" vs. "edit"

| Option                                                                                                                                                                                                                                                                                                                                                         | Pros                                                                                                                                                                                                                                                                                                                                    | Cons                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A: extend `BookmarksStore` with an `editing` signal (`{ id: number; updatedAt: string } \| null`) and a `beginEdit(bookmark)` method; extend `BookmarkForm` with an `openEdit(bookmark, opener)` method mirroring `open()`. The template reads `store.editing()` to switch the dialog title, the submit button's label, and which HTTP verb `save()` calls** | This **is** C-F06-02/C-F06-03's "reuse the same dialog" — zero duplicated markup, zero duplicated tag-chip wiring, zero duplicated focus-trap or `Esc` handling. `opener` is already a generic parameter on `open()`, so F06-AC13's "`Esc` returns focus to the row's own _Edit_ button" works with no new focus-management code at all | `BookmarkForm`/`BookmarksStore` grow a small number of F06-only members — the same incremental-ownership pattern F02 (the tag slice) and F03 (the list slice) already established on this exact store                                                                     |
| B: a second, separate `BookmarkEditForm` component/dialog                                                                                                                                                                                                                                                                                                      | Total isolation from F01's code; no risk of an edit-only bug touching the add path                                                                                                                                                                                                                                                      | **Contradicts the already-approved spec outright** (C-F06-02, C-F06-03, F06-AC1 all commit to one form, ported from `docs/mockup.html`'s single `openForm(b)`). **Trade-off accepted:** `BookmarkForm`/`BookmarksStore` carry both the add and edit paths in one component pair, in exchange for the dialog, tag input, focus trap and keyboard contract never being able to drift between the two modes.
**Challenge applied:** _what breaks on a title-fetch failure?_ Nothing new — `userTitle === ''` still routes to the fetcher exactly as in F01, regardless of `editing()`, per C-F06-02's "re-runs the identical fetch-or-hostname-fallback logic … regardless of whether the URL changed". _On restart?_ N/A, client-only state. _Keyboard-only?_ F06-AC13 is written against exactly this shape — the same native `<dialog>`, the same tab order, the same chip-input keys F02-AC10 already established, with only the `Esc`-restores-focus-to-_which_-button detail changed by `opener`.

## 5. Data Access

**No entity, field, index, or invariant is added, changed, or removed.** Every table and index already exists in `data-model.md` v3; `updated_at` already exists and already documents "EC21 conflict detection" as its purpose (`data-model.md` §1).

| Entity         | F06 use                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `bookmark`     | Read (by id for the `NOT_FOUND`/conflict check; by normalized-url-excluding-self for the duplicate check) and write (`UPDATE`, never touching `created_at` or `id`)                                    |
| `tag`          | Written via the existing `upsertAndGetId` (F02), for any newly-introduced tag name                                                                                                                     |
| `bookmark_tag` | Rewritten as a set inside the update transaction: every existing link for the id is deleted, then the final tag list is re-linked (HLD §6.3: "Tags are replaced as a set inside the same transaction") |
| `setting`      | Not used                                                                                                                                                                                               |

**Indexes used:** `ux_bookmark_url_live` (the self-exclusion lookup and the `UPDATE`'s own constraint check), `bookmark_tag`'s composite primary key (the delete-then-relink). `ix_bookmark_list` is untouched by an edit — `created_at` never changes, so no row's position in that index's ordering changes (INV-10, F06-AC7).

**Queries** — prepared statements only (S4); no value is ever concatenated into SQL.

| Function                                                  | Statement (described)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `findLiveById(id)`                                        | Already exists from F01: `SELECT … FROM bookmark WHERE id = ? AND deleted_at IS NULL`. Reused unchanged for the `NOT_FOUND`/conflict fetch                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `findLiveByNormalizedExcluding(urlNormalized, excludeId)` | `SELECT id, url, title, title_source, created_at, updated_at FROM bookmark WHERE url_normalized = ? AND deleted_at IS NULL AND id <> ?` — index seek on `ux_bookmark_url_live` plus an equality filter (LD-02)                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `update(id, row, tagNames)`                               | `UPDATE bookmark SET url=?, url_normalized=?, title=?, title_source=?, updated_at=? WHERE id = ? AND deleted_at IS NULL` (no `created_at` in the `SET` list — INV-10). If `changes === 0` (the row was soft-deleted between the service's existence check and this statement — a genuine but narrow race), throws `AppError NOT_FOUND` rather than silently no-op-ing. Then `DELETE FROM bookmark_tag WHERE bookmark_id = ?`, then for each name in `tagNames`: `upsertAndGetId` + `link` (both already exist, F02). Wrapped in one `better-sqlite3` transaction, so a crash mid-write rolls back the row update together with the tag-set replacement (NFR-02, EC19) |

**Service orchestration (`bookmark-service.update(id, payload)`):** `validateUrl` → `validateUserTitle` → `tagService.normalizeAndValidate` → `repository.findLiveById(id)` (404 if absent) → compare `payload.updatedAt` to the fetched row's `updated_at` (409 `EDIT_CONFLICT` on any mismatch, LD-01) → `normalizeUrl` → `repository.findLiveByNormalizedExcluding` (409 `DUPLICATE_URL`, with `tags` fetched via the existing `listTagsForBookmarks([dup.id])` for the response `details`, LD-03) → title decision (identical to `create()`'s, re-run whenever no user title is supplied, C-F06-02) → `repository.update(...)`.

## 7. Validation Rules

All validation is performed in `api` at the boundary and is the only validation that counts (S1), identically to F01/F02. F06 adds exactly one new rule; the rest are the same functions, re-invoked, not re-implemented.

| Field             | Rule                                                                                                                                                                                                                                                                                                                                        | User message                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url`             | Reused verbatim: `validateUrl()` (HLD v3 §8 order, rules 1–5 — trim/non-empty, ≤ 2048, parses, scheme allow-list, hostname-contains-a-dot)                                                                                                                                                                                                  | Identical to F01's three messages (F06-AC5 is representative; F01's remaining messages apply identically, per `spec.md` §5 — not restated)                                                               |
| `title`           | Reused verbatim: `validateUserTitle()` (≤ 140 when user-supplied, INV-05)                                                                                                                                                                                                                                                                   | `That title is too long (limit 140 characters).`                                                                                                                                                         |
| `tags`            | Reused verbatim: `tagService.normalizeAndValidate()` (shape, length 1–24, charset allow-list, ≤ 8, optional per C-F02-05). An update whose final tag list is empty is **not** a validation failure — it reuses F02's existing "tags are optional" rule unchanged, so editing the tags down to zero succeeds and stores `tags: []` (F06-EC1) | Identical to F02's messages (F06-AC6 is representative; F02's remaining messages apply identically — not restated)                                                                                       |
| `updatedAt` (new) | Must be present, a string, and exactly equal the stored row's `updated_at`. Any other case — missing, wrong type, or a mismatched value — is treated identically: the server cannot trust the claim, so it refuses rather than coerces or defaults (AMD-003, LD-01)                                                                         | `This bookmark changed in another tab. Reload to see the latest, then try again.` (status 409, not 400 — this is the concurrency guard operating as designed, not a shape mistake the user needs to fix) |

Order is fixed, first-failure-wins, identical in spirit to F01's rule: `url` → `title` → `tags` → row-existence (`NOT_FOUND`) → `updatedAt` conflict → duplicate-exclude-self. Validating the three reused fields completely before any row lookup keeps F06 from re-deriving an ordering F01 already fixed; no acceptance criterion in `spec.md` depends on a different order between the two new checks and the reused three.

## 8. Error Handling

| Condition                                                                                                                  | Detected where                                                                                                                                            | Response / UI feedback                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Empty/invalid URL, over-length title, invalid tag shape (F06-AC5, F06-AC6)                                                 | `bookmark-service.update()`, reusing `validateUrl`/`validateUserTitle`/`tagService.normalizeAndValidate` unchanged                                        | `400 INVALID_URL` or `400 INVALID_TAG`, identical messages to F01/F02. **No row is modified** — detected before any lookup                                                                         |
| The bookmark no longer exists as a live row (soft-deleted elsewhere, F06-AC10, EC21)                                       | `bookmark-service.update()`'s `repository.findLiveById(id)` returns `null`                                                                                | `404 NOT_FOUND`, message `That bookmark is no longer here.`, shown in the dialog's new alert banner. **No row is created or resurrected**                                                          |
| `updatedAt` missing, wrong type, or not equal to the stored row's `updated_at` (F06-AC11, EC21)                            | `bookmark-service.update()`, compared against the row just fetched for the `NOT_FOUND` check — **server-side only** (S1, AMD-003)                         | `409 EDIT_CONFLICT`, the AMD-003 message, with a _Reload_ action. **The stored row keeps the other tab's values** — never overwritten                                                              |
| Edited URL collides with a different live bookmark, found before the `UPDATE` (EC16, F06-AC4)                              | `bookmark-service.update()` via `findLiveByNormalizedExcluding`                                                                                           | `409 DUPLICATE_URL` with `existingId` and `details { title, url, tags, updatedAt }` — the same banner/`View existing`/`Edit existing` contract as F01-AC11. **This record's own row is unchanged** |
| Resaving the record's own unchanged URL (F06-AC3, F06-EC2)                                                                 | The same `findLiveByNormalizedExcluding` call — excludes `id`, so the record never collides with itself                                                   | `200`, not `409` — this is the INV-04 self-exclusion the lookup exists to guarantee                                                                                                                |
| Duplicate detected only by the unique index at `UPDATE` time (a race symmetrical to F01's LD-02, EC21)                     | `bookmark-repository.update()` catches `SQLITE_CONSTRAINT_UNIQUE`, re-reads the colliding row via `findLiveByNormalizedExcluding`, rethrows as `AppError` | Byte-identical `409 DUPLICATE_URL` body to the pre-update-lookup path — both call the same `duplicateUrlError()` builder (P6)                                                                      |
| The row is deleted between the `findLiveById` existence check and the `UPDATE` itself (a narrower race than the one above) | `bookmark-repository.update()`'s `changes === 0` check                                                                                                    | `404 NOT_FOUND` — the same response the earlier, more common race produces                                                                                                                         |
| Title fetch runs and fails (no user title supplied, F06-AC8)                                                               | `bookmark-service.update()`'s title decision — identical to `create()`'s                                                                                  | **Not an error — `200`.** `title_source = 'hostname'`, and the F01-AC5 toast notice appears **in place of** `Changes saved` (F06-AC8, C-F06-02)                                                    |
| Database failure on update                                                                                                 | `bookmark-repository.js` → the existing `app.js` error middleware (unchanged)                                                                             | `500 STORAGE_ERROR`, the existing safe message; full detail to the server console only (U5)                                                                                                        |

**One rule this table encodes, specific to F06.** `EDIT_CONFLICT` and `NOT_FOUND` are both races that F01's create path cannot experience at all (there is no "the row I'm editing" for a create), so neither is a copy of an existing F01/F02 error — both are new branches in `update()`, not new rules inside the reused validators.

## 9. Security Considerations

One row per untrusted input F06 touches or adds, per the `secure-input-handling` skill. Every row already listed in F01's `lld.md` §9 for `url`, `title`, and F02's for `tags` applies unchanged on `PUT` and is not restated.

| Untrusted input                                          | Control applied                                                                                                                                                                                                                                                                                     | Constitution clause                                                                                             |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Submitted `updatedAt` (new)                              | Compared by exact string equality against the row's own stored `updated_at`, fetched server-side by id — **never** supplied by, or trusted from, the client beyond this one comparison. Missing or wrong-typed is treated identically to mismatched: rejected, never coerced or defaulted (AMD-003) | **S1** — the server decides whether a conflict exists; the client's claim that it resolved one is never trusted |
| `:id` route parameter                                    | Used only as a bound parameter in `findLiveById`/`update`'s `WHERE id = ?`; never concatenated; a non-numeric or absent id simply matches no row and produces the existing `404 NOT_FOUND` path, not a 500                                                                                          | **S1**, S4                                                                                                      |
| Edited URL — duplicate-lookup self-exclusion             | `findLiveByNormalizedExcluding`'s `id <> ?` is itself a bound parameter (the id from the route, already validated as "exists" by the prior `findLiveById` call) — never a string-built clause                                                                                                       | **S4**                                                                                                          |
| Tags in the `DUPLICATE_URL` response's `details` (LD-03) | Read from `bookmark_tag`/`tag` via the existing, unchanged `listTagsForBookmarks`; rendered through Angular interpolation only when the banner displays them, exactly as F03's cards already do — never `[innerHTML]`                                                                               | **S3**                                                                                                          |

**Not applicable in F06:** search text, tag-filter values, `setting` key/value (S6, N/A rows) — none is touched by an edit.

## 11. Test Hooks

- **`bookmark-service.update(id, payload)` accepts the same raw, possibly-invalid values the route passes through** — tests call it directly, exactly as `create()`'s tests already do, without needing a running server.
- **Two sequential `service.update()` calls against one `:memory:` db, using the FIRST call's success response's `updated_at` for the second call's STALE `updatedAt`**, is how F06-AC11 is made deterministic with no real concurrency, no timers, and no two actual clients — simulating "two tabs" as two calls in one test.
- **`findLiveByNormalizedExcluding` and the race-detecting `update()`'s `changes === 0` branch** are both exercised against the real `:memory:` SQLite engine (reusing F01's `createDb({ file: ':memory:' })` seam) so the genuine unique index and the genuine row-count semantics are what the test observes, not a stub.
- **`editConflictError()` and the extended `duplicateUrlError(existing, tags)`** are exported as pure functions so a test can assert the exact response body shape without going through HTTP.
- **`ApiService` provided through Angular DI** with `provideHttpClientTesting` (the existing F01/F03 pattern) — the edit dialog's 400/404/409×2/200 branches are testable without a server.
- **`BookmarksStore.beginEdit()`/`openEdit()`** are tested the same way F03's `loadList()` request-token guard already is: calling them directly and asserting the resulting signal values, with no real dialog element needed for the store-level assertions.
- **Deliberately not automated in F06, carried to `/test-phase F06-edit-bookmark`:** the real multi-tab scenario (two actual browser contexts) — the two-sequential-calls simulation above is what stands in for it, same pattern F01 used for its own restart check (a documented, reasoned substitution, not an oversight). F06-AC13's keyboard walkthrough is a manual, recorded procedure, matching F01-T12/F02-T12's precedent.

## 12. Architecture Impact

**One amendment, raised and applied in this same session: AMD-003.** `hld.md` moved from v2 to **v3**: §8's error-handling table gained one row (`EDIT_CONFLICT`, 409, the exact message above) and its trust-boundary table gained one row (the submitted `updatedAt`, compared server-side only). `data-model.md`, `er-diagram.md`, and `component-map.json` are all unchanged — `updated_at` already existed and already documented "EC21 conflict detection" as its purpose, so no schema object changed and no migration is required (the same conclusion AMD-001 and AMD-002 both reached for their own, unrelated reasons).

This closes **F06-RK1**, the risk `specs/features/F06-edit-bookmark/spec.md` §6 raised at planning: "`/design-feature F06-edit-bookmark` must raise an amendment adding `EDIT_CONFLICT` to `hld.md` §8 … before F06-AC11 can be built against an approved contract." dev-1 chose, when asked, "Option A: raise AMD-003, apply it before finalizing the LLD" — so this LLD is written directly against the post-amendment HLD rather than against a still-open risk.

No other architecture-impact candidate was found while writing this design. The `DUPLICATE_URL` response's `details` object gaining `tags`/`updatedAt` keys (LD-03) is **not** an architecture change: `hld.md` v3 fixes `existingId` as a specific field of the error body but leaves `details` as an extensible object (it already varies — F01's `duplicateUrlError()` populates `{ title, url }` and nothing in HLD enumerates `details`'s keys as closed), so adding keys to it is an additive LLD decision, the same class of decision F02 made when it extended the create payload with `tags` without an amendment.
