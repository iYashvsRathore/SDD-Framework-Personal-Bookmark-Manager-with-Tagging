# AMD-003: Add `EDIT_CONFLICT` to the error-handling and trust-boundary tables

**Status:** Applied (2026-10-01) · apply gate approved by dev-1 on 2026-10-01
**Raised by:** F06-edit-bookmark / design / dev-1
**Date:** 2026-10-01
**Blocks:** — (cleared on apply; previously F06-edit-bookmark, design)

## 1. Problem

`specs/features/F06-edit-bookmark/spec.md` F06-AC11 is an approved acceptance criterion requiring optimistic-concurrency conflict detection on edit: if a bookmark is edited in one tab while another tab's edit dialog is still open on the pre-edit values, saving the stale edit must return `409 EDIT_CONFLICT` rather than silently overwriting the newer values. dev-1 ruled for this behavior at the planning gate (C-F06-01, 2026-10-01), explicitly over last-write-wins.

`hld.md` v2 §8 defines exactly one internal error type (`AppError`) and a closed error-handling table (`INVALID_URL`, `DUPLICATE_URL`, `INVALID_TAG`, `NOT_FOUND`, `STORAGE_ERROR`) plus a closed trust-boundary table. `EDIT_CONFLICT` is not a member of either. `data-model.md`'s `updated_at` column already documents "EC21 conflict detection" as its purpose, so the _field_ is architecturally anticipated, but the _response contract_ — status code, error code, and the comparison rule — is not yet approved. Writing F06's LLD against an error code the shared HLD does not describe would be exactly the E3 drift AMD-001 and AMD-002 both exist to prevent: `/review-phase` would later compare F06's code to `hld.md` and find a response the architecture never approved.

This was recorded plainly as risk **F06-RK1** in `specs/features/F06-edit-bookmark/spec.md` §6 and carried forward as a blocker in `status.md`, naming this exact fix — add `EDIT_CONFLICT` to `hld.md` §8's error-handling table and its trust-boundary table — before the LLD can be finalized.

## 4. Impact Analysis

- **Features affected:**
  - **F06-edit-bookmark** — this is the amendment F06-RK1 named as a precondition for finalizing `lld.md`. Unblocks the design gate; `lld.md` is written directly against the new row (status, message, and comparison rule all come from this file verbatim, not re-derived).
  - F01, F02, F03, F04 — unaffected. None returns or consumes `EDIT_CONFLICT`.
  - F07-delete-bookmark (not yet planned) — may eventually face the same two-tab race on delete (EC21 already names "two browser tabs edit or delete the same bookmark"). Not addressed here: F06's conflict check is edit-specific (compares `updated_at` on a `PUT`), and HLD §6.4's existing `NOT_FOUND`-on-already-deleted path already covers the delete side of EC21 without a new code. If F07 needs something more than that, it raises its own amendment then — not anticipated here, per P4.
- **Migration/backward compatibility:** none required. No schema object changes — `updated_at` already exists and is already populated on every row by F01's insert path, so no migration and no `user_version` bump (same conclusion as AMD-001 and AMD-002, for the same reason).
- **Test impact:** `/test-phase F06-edit-bookmark` gains the F06-AC11 conflict-detection probe (stale `updatedAt` after a concurrent edit → 409) as its own test, once F06 is built.
- **Constitution check:** pass. **S1** — the conflict decision is explicitly server-side only; the client's claim is never trusted. **P3** — the trust-boundary row states plainly that the comparison is "exact string equality," not a fuzzy or best-effort check, so nothing is overstated. **P4** — one row in each of two existing tables; no new table, no new dependency, no new persisted field. **E3** — resolves the disagreement this amendment exists to prevent, the same reasoning AMD-001 and AMD-002 both used.
